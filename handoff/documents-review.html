Draft integration specification

Document portal integration

Scope: document requests initiated in Emumba’s advisor portal or Neoserra, with all client actions routed through MySBDC. This document defines the required behavior, proposed approach, and integration decisions to resolve.

Requirements and proposed approach

Requirement

Client routing

Document requests are advisor initiated and case by case. The client sees the request, uploads files, receives confirmation, and accesses returned documents through MySBDC. Client-facing notification links lead back here. Failed or unrelated uploads never clear the request.

Proposal

Request component

Cameron provides a dedicated MySBDC component that receives structured request data. Where supported, Emumba owns document-request IDs and status; a Neoserra action references the same request. Reopening it must not create duplicates. The supporting API is not yet confirmed.

Open decision

Integration and placement

Confirm the portal’s request-creation capability and delivery mechanism, plus Neoserra field/link support. Agree ownership, IDs, creation timing, edits, withdrawal, and completion signals. Submit a placement and priority proposal for product review when a separate note and request coexist.

Suggested ownership: Aaron confirms the experience and acceptance criteria. Cameron coordinates MySBDC and Neoserra integration with Emumba, who confirms the portal’s supported behavior.

Integration questions

Owners: Cameron and Emumba. Confirm the supported interfaces and propose the implementation. The supplied vendor JavaScript is unchanged.

Demo boundary: no production request is created or completed. Returning Home keeps the sample note visible. Completion and the Done receipt require the agreed integration.

Emumba request → MySBDC
Can an advisor create a request from the client-document library? Confirm the supported request ID, client/advisor mapping, request text, status, and API or event delivery to MySBDC. The client should not need a separate portal login or destination.
Neoserra note → the same client experience
Can the API expose the custom field and a reliable note version or change signal? Agree the recognized link/action format and whether it references an existing portal request or creates one. Creation on note save versus first open remains open for this route.
Dashboard routing & placement
Request and notification links resolve inside MySBDC, returning the client to the intended request after sign-in. Confirm account access before opening it. Propose how a dedicated request component fits with an unrelated next-step note; do not duplicate one request in two cards.
Signed token
Please confirm the token fields, signing method, expiration, and a server-side example. This is the authentication token in data-token, separate from the advisor’s note.
Domain & release
Send the staging and production hostname requirements, exact DNS records, approved script URL and integrity hash, and any iframe or cross-origin requirements.
Sign-out
Send the supported session-close call, whether we should await it, and how failure should be handled when the client signs out of MySBDC.
Confirmed actions
We need supported upload and download signals with the relevant request, upload or document ID, outcome, and time. An unrelated upload must not clear an advisor’s request.
Document & request status
Confirm how to identify returned documents not yet downloaded, and how an upload is matched when several requests exist. The current “Ready for you” count includes downloaded files.
Supported styling
Confirm the supported theming hooks. This preview uses the theme properties plus CSS inside the open shadow root; the vendor JavaScript is not edited.
